# Workflow

_How work moves through this project. Generated by /bootstrap-project on 2026-08-23;
referenced by /start-task on every task._

## Modes

- **GUIDE** — default during bootstrap and at the start of a task: ask questions, explain
  options, recommend a workflow. No spawning, no writes.
- **COORDINATE** — after the user approves a task's workflow/plan: spawn read-only role
  agents (Argus, Athena, Themis, Apollo), validate their output, prepare the Codex handoff.
  Still no production writes.
- **EXECUTE** — only within an approved task, only for the approved scope: run the Codex
  handoff, run verification commands. Anything outside the approved scope drops back to
  GUIDE.

## Standard workflow by task type

| Work type | Workflow |
|---|---|
| Small, low-risk fix (typo, single broken link, one field correction) | Argus → Codex → Apollo |
| New site section / build-plan task (docs/08 row) | Argus → Athena → **approval** → Codex → Themis → Apollo |
| UI / interactive component change | Argus → Athena → **approval** → Codex → Apollo (visual/runtime check at 375/768/1280, both themes) |
| `plans.yaml` / `models.yaml` data change | Argus (+ data-verifier pass) → **approval** → merge — no Codex needed, this is data not code, but the human-verification approval gate is non-negotiable (ADR-003) |
| Milestone boundary (M0→M1, M1→M2, etc.) | Parallel Themis review across the whole completed milestone (this is what `phase-reviewer.md` specializes) → dedup → user |
| Content-only page (concept, prompt, playbook, etc.) | Argus → `page-drafter` (writer) → Themis (schema/taxonomy/neutrality conformance, via `content-auditor.md`) |
| Architecture or stack change (new dependency, schema shape) | Argus → Athena → independent Themis review → **approval** |

Bold **approval** = hard stop; do not proceed without explicit user sign-off.

## How this project's site-content agents fit in

`.claude/agents/` holds five agents that are dual-purpose: they are working build tooling
**and** published site content under `/agents/profiles/`. They are not a substitute for the
Argus/Athena/Themis/Apollo roles above — they're narrower, content-specific tools that a
role invokes:

| Site-content agent | Invoked by | Scope |
|---|---|---|
| `page-drafter` | Codex-handoff step, or directly for content-only work | Drafts one content page from its type template |
| `content-auditor` | Themis | Checks frontmatter/tag/template conformance across a batch of pages |
| `data-verifier` | Argus, on a data-change task | Re-verifies plan/model facts against provider sources; never merges |
| `field-report-triager` | Argus, on the rolling report queue | Converts submitted issues into validated `field-reports.yaml` entries |
| `phase-reviewer` | Themis, specifically at milestone boundaries | The milestone-boundary row above — adversarial review of a whole completed phase |

## Codex handoff

Implementation is delegated via `codex exec` using the handoff template in
`~/.claude/skills/start-task/templates/handoff-codex.md`. The handoff prompt and the
resulting diff are both shown to the user — the handoff itself does not require a separate
approval step beyond the plan approval that already authorized this phase of work, but the
diff is reviewed before anything is committed.

In practice on this project so far: Codex works on a task branch (`m0-t{n}-{slug}`), opens
a PR against `main`, CI (`.github/workflows/ci.yml`) must pass, then merges. All five M0
PRs followed this pattern successfully — continue it unchanged for M1 onward.

## Git / commit strategy

- One task branch per `docs/08-build-plan.md` row (or sub-grouping of closely related
  rows), named `m{milestone}-t{task}-{short-slug}`.
- PR against `main`; CI must be green before merge.
- No direct pushes to `main`.
- Never force-push; never rewrite history on `main`.
- Milestone boundaries get a Themis (phase-reviewer) pass before the next milestone's first
  branch is opened.

## Data safety policy

No database, no auth, no irreplaceable local data — the repo plus its GitHub remote is the
durable store. Standard git safety protocol applies (never discard uncommitted work without
checking `git status` first; stash before any destructive operation). No additional backup
policy is needed beyond that.

The one data-specific rule: changes to `src/data/plans.yaml` or `src/data/models.yaml` are
never auto-merged by an agent, regardless of how they were generated (ADR-003,
`.claude/agents/data-verifier.md`). A human confirms the source before merge.
