## Problem it solves

Starting from a vague request invites polished work that solves the wrong problem. A brief gives the person and the assistant one shared target before effort accumulates.

## Structure

```text
request -> assumptions -> brief -> review -> build
```

Each arrow is a checkpoint: do not advance while a decision is still hidden inside an assumption.

## Example

A teammate asks for a launch page. First capture the audience, conversion action, required proof, and approval owner. Review that brief together; only then draft the page and check it against the agreed outcome.

## Tradeoffs

The pattern adds a small upfront step and can feel slow for trivial work. It earns its cost when revision, handoff, or a wrong decision would take longer than writing the brief.

## Related patterns

Use a review-against-criteria pattern after the build, and a handoff brief when the work crosses sessions or people.
